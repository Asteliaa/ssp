# Теория: платформа .NET, IL-код и JIT-компиляция

## 1. Модель выполнения .NET

Код на C#, F#, VB.NET и других языках платформы .NET не компилируется
напрямую в машинный код процессора. Компилятор языка (например, `csc` —
компилятор C#) переводит исходный текст в промежуточный язык —
**IL (Intermediate Language)**, также называемый **CIL** (Common Intermediate
Language) или историческим термином **MSIL**. Результат сохраняется в
сборку (assembly, файл `.dll`/`.exe`) вместе с метаданными о типах, методах
и их сигнатурах.

Непосредственно перед выполнением метода среда выполнения **CLR**
(Common Language Runtime) вызывает **JIT-компилятор** (Just-In-Time),
который переводит IL этого конкретного метода в машинный код,
специфичный для процессора и операционной системы, на которых
запущена программа. Скомпилированный машинный код кэшируется в памяти
процесса — повторные вызовы того же метода уже не требуют повторной
компиляции.

Такая двухступенчатая схема (сначала в IL, затем в машинный код) даёт:

- **переносимость** — одна и та же сборка `.dll` выполняется на Windows,
  Linux и macOS, на x64 и ARM64 — JIT генерирует код под конкретную
  платформу непосредственно в момент запуска;
- **возможность оптимизации под конкретное железо** — JIT знает набор
  инструкций процессора, на котором реально выполняется программа,
  и может использовать, например, векторные инструкции AVX2, если
  они доступны;
- **интероперабельность языков** — любой язык, компилятор которого
  умеет генерировать IL, автоматически получает доступ ко всей
  экосистеме .NET.

## 2. Устройство IL-кода

IL — это байт-код для **стековой виртуальной машины**: у инструкций
нет операндов-регистров, вместо этого они читают аргументы с вершины
вычислительного стека и кладут туда результат.

Например, C#-выражение `a + b` компилируется в последовательность:

```
ldarg.0   // положить на стек первый аргумент (a)
ldarg.1   // положить на стек второй аргумент (b)
add       // снять два верхних значения, сложить, положить результат
ret       // вернуть значение с вершины стека
```

### Основные категории IL-инструкций

| Категория | Примеры инструкций | Назначение |
|---|---|---|
| Загрузка/сохранение | `ldarg`, `ldloc`, `stloc`, `ldc.i4` | работа со стеком, локальными переменными, константами |
| Арифметика | `add`, `sub`, `mul`, `div`, `neg` | вычисления |
| Сравнение и переходы | `beq`, `bgt`, `blt`, `br`, `brtrue` | реализация `if`, `while`, `for` |
| Вызовы методов | `call`, `callvirt`, `newobj` | вызов статических/виртуальных методов, создание объектов |
| Работа с объектами | `ldfld`, `stfld`, `box`, `unbox` | доступ к полям, упаковка значимых типов |

### `stloc` против `starg`

Это частый вопрос на защите, поэтому явно зафиксируем разницу:

- **`stloc` (store local)** сохраняет значение с вершины стека в
  **локальную переменную** метода (объявленную через `DeclareLocal`
  в терминах `ILGenerator` или обычным `int x;` в C#).
- **`starg` (store argument)** сохраняет значение с вершины стека
  обратно в **параметр метода** — то есть переприсваивает входной
  аргумент внутри тела метода (в C# это соответствует присваиванию
  значения параметру: `void M(int x) { x = 5; }`).

Ключевое отличие — область действия: локальные переменные существуют
только внутри метода и не видны вызывающему коду, а параметры — это
именованные слоты, через которые метод получает данные извне.

### Информация о теле метода

Через рефлексию (`MethodInfo.GetMethodBody()`) можно получить объект
`MethodBody`, который содержит:

- `GetILAsByteArray()` — сырые байты IL-кода метода;
- `LocalVariables` — список локальных переменных и их типов;
- `MaxStackSize` — максимальная глубина вычислительного стека,
  необходимая для выполнения метода (CLR резервирует под неё память
  заранее, поэтому JIT обязан её точно знать).

Это доступно **только для методов, тело которых физически присутствует
в сборке** — в частности, оптимизирующий компилятор в конфигурации
Release иногда не сохраняет отладочные метаданные, из-за чего
`GetMethodBody()` может вернуть `null` (отсюда требование собирать
лабораторную в Debug).

## 3. JIT-компиляция

### Normal JIT

Классическая схема: метод компилируется **при первом вызове**,
целиком и сразу с максимальным уровнем оптимизации. Плюс — итоговый
код исполняется быстро; минус — сама компиляция занимает заметное
время, что даёт задержку ("холодный старт") при первом обращении
к каждому методу.

### Tiered Compilation (многоуровневая компиляция)

Начиная с .NET Core 3.0 и включённая по умолчанию в .NET 8, CLR
использует адаптивную стратегию:

1. **Tier 0** — метод при первом вызове компилируется быстро,
   но без глубоких оптимизаций (используется quick JIT). Это резко
   сокращает задержку холодного старта.
2. **Tier 1** — если метод вызывается часто (CLR отслеживает счётчик
   вызовов), в фоновом потоке он перекомпилируется повторно, уже
   с полным набором оптимизаций, и "горячий" код подменяется на
   оптимизированный без остановки выполнения программы.

Таким образом Tiered Compilation — это компромисс между временем
запуска приложения и производительностью часто выполняемого кода:
редко вызываемые методы остаются на "быстром, но грубом" Tier 0,
а по-настоящему "горячие" участки дожидаются полной оптимизации.

Управляется в `.csproj`:

```xml
<PropertyGroup>
  <TieredCompilation>false</TieredCompilation>
</PropertyGroup>
```

### Как JIT оптимизирует часто вызываемые методы

Помимо повторной компиляции с более сильными оптимизациями (Tier 1),
JIT применяет к горячим методам:

- **инлайнинг (inlining)** — тело маленького метода подставляется
  прямо в место вызова, убирая накладные расходы на сам вызов
  (создание кадра стека, переход по адресу и обратно);
- **устранение проверок границ массива**, если доказуемо, что индекс
  всегда в допустимых пределах;
- **регистровое распределение** — часто используемые переменные
  держатся в регистрах процессора, а не в памяти;
- **профильно-управляемые оптимизации (PGO)** — начиная с .NET 8,
  Tier 1 может использовать реальную статистику выполнения (какие
  ветки `if` чаще срабатывают, какие типы чаще встречаются при
  вызовах через интерфейс) для более точной оптимизации.

Виртуальные вызовы (`callvirt`) и вызовы через делегаты сложнее
поддаются инлайнингу, чем прямые статические вызовы, так как
конкретный адрес целевого метода в общем случае не известен на этапе
компиляции — это демонстрируется в Задании 5.

## 4. Динамическая генерация кода: `ILGenerator` и `DynamicMethod`

Класс `System.Reflection.Emit.DynamicMethod` позволяет создать метод
**во время выполнения программы**, минуя стадию написания и
компиляции C#-кода. Единственный способ получить `ILGenerator` —
вызвать `DynamicMethod.GetILGenerator()`: генератор IL всегда
привязан к конкретному динамическому методу, который он наполняет
инструкциями.

Типичный сценарий работы:

1. Создать `DynamicMethod`, указав сигнатуру (тип возвращаемого
   значения и типы параметров).
2. Получить `ILGenerator` и последовательно вызывать `Emit(...)`,
   формируя IL-инструкции — ровно так же, как это делает компилятор
   C#, только вручную.
3. Превратить готовый метод в делегат через `CreateDelegate`
   и вызывать его как обычную C#-функцию.

Такой подход применяется, когда сигнатуру и логику метода нельзя
знать заранее на этапе компиляции — например, в ORM-библиотеках
(генерация методов доступа к полям сущностей), сериализаторах,
интерпретаторах шаблонов выражений (`Expression Trees`), генераторах
прокси-объектов и compiled regex.

## 5. Измерение производительности: BenchmarkDotNet

Наивное измерение времени через `Stopwatch` вокруг одного вызова
метода даёт очень шумную и часто вводящую в заблуждение цифру:
на неё влияют JIT-компиляция при первом вызове, "прогрев" процессора
и кэшей, работа сборщика мусора, планировщик ОС. **BenchmarkDotNet** —
стандартная в экосистеме .NET библиотека, которая решает эту проблему:

- выполняет фазу **Pilot** — подбирает число повторов внутри одной
  итерации так, чтобы её длительность была статистически измеримой;
- выполняет фазу **Warm-up** — прогревает JIT и кэши процессора
  до того, как начнутся "боевые" замеры, тем самым **намеренно
  исключая время JIT-компиляции** из итоговой цифры;
- проводит несколько независимых итераций и считает среднее,
  медиану, стандартное отклонение;
- опционально измеряет выделения памяти в управляемой куче
  (`[MemoryDiagnoser]`).

Именно поэтому в лабораторной работе влияние самой JIT-компиляции
(холодный вызов) измеряется отдельно, вручную через `Stopwatch`
и `RuntimeHelpers.PrepareMethod` — BenchmarkDotNet для этой цели
принципиально не подходит, так как специально абстрагируется от
холодного старта.

## 6. Ключевые термины (для контрольных вопросов)

| Термин | Определение |
|---|---|
| IL / CIL / MSIL | Платформо-независимый байт-код, в который компилируется исходный код языков .NET |
| CLR | Common Language Runtime — среда выполнения, управляющая памятью, потоками, JIT-компиляцией |
| JIT | Компиляция IL в машинный код непосредственно перед первым выполнением метода |
| Tiered Compilation | Адаптивная стратегия JIT: сначала быстрая грубая компиляция (Tier 0), затем — для горячих методов — полная оптимизация (Tier 1) |
| Холодный старт | Задержка первого вызова метода, вызванная временем его JIT-компиляции |
| Инлайнинг | Подстановка тела метода в место вызова вместо реального вызова, устраняющая накладные расходы |
| `ILGenerator` | API для пошаговой генерации IL-инструкций динамического метода |
| `DynamicMethod` | Класс, представляющий метод, полностью созданный во время выполнения программы |
